# 032: Mods loaded from disk at run time (#28, research)

Research record, 2026-11-15; read-only, no device action. Open-XY from a fresh upstream clone (`paths.OPEN_XY_UPSTREAM`), `staging` tip **`ba943a8`** (fetched 2026-11-15, unchanged since record 028); paths below are in it unless they start with `native/` or `docs/`. Packages: the published 0.0.6 set (`paths.PUBLISHED_MODS`; `info.txt` `code/data/state`). Tags: **[C]** our code, **[O]** open-xy, **[M]** measured, **[I]** inferred, **[U]** unknown.
**In brief.** Feasible in principle, and the stock OS already gives the decisive pieces: an engine is known to stock only through a 48-byte record that the SDK *registers at run time* through stock's own registrar (factory and parameter-name pointers, name, ID, page), and a project hook already reads files on the GUI role before a loaded project becomes active. But it is mostly **Open-XY runtime work**, the arena must stay a **reserved region** (not the stock heap), and the selection limit becomes a per-project limit, not no limit. **Recommendation:** a first experiment with one machine, after the maintainers answer §8 Q1-Q4.
## 1. How a machine is known to the OS today
- **Records, filled at boot.** Stock's engine, effect and screen-page tables are relocated once into the reservation with fixed room: 256 engine, 63 effect, 256 page slots (`tooling/stock_tables.py:47-56`), independent of the selection. The SDK fills them at the synth initializer's exit (`startup_exit.s:15`) via stock's registrar `0x8d50651c` (`registration_stock.cpp.in:31-46`); stock clears and refills them each run (`docs/abi-1.2.1.md:233-243`). So registration is already dynamic [O].
- **One indirection point per synth exists.** Stock calls only the record's `factory(index)` and the 11-entry method table it returns; it "never checks for a missing one" (`voice.cpp.in:1-17,222-228`). A base-held stub factory returning a silent handle can stand in until the body is loaded [I].
- **What is fixed at build:** the per-collection SDK glue. `startup.cpp.in` (generated by `tooling/startup.py:60-123`) calls each machine's `_register`, `_name_matches`, `_ready`, `_screen_register`, `_screen_ready` and its ID symbols directly: these are the 11 sites of record 028; `benchmark.o` (6, profiling only) and `sdk_companion_machines[]` (2, `project_companion_table.cpp.in`) are the rest. All become reads through a per-machine slot table. Names, labels (`_parameter_name`), IDs and pages must stay in the base, since menus and presets ask before any load (`presets.cpp`, `sdk_engine_installed`).
- **Own screens:** a machine's screen object lives in its BSS and registers at the GUI screen factory's exit (`abi:236`); 23 packages have a page of their own (15 synths, 7 effects, 1 sample). Late registration after startup is [U].
- **Content:** catalog entries in `op1_factory.json` and presets are files; with every installed machine registered, content changes only on install/remove [I].
## 2. What Open-XY code runs inside the OS, and when
- **File access:** newlib `fopen/fread/fwrite/fclose` at `0x8fed0348/05bc/0780/00ae` (`project_files.hpp:12-21`), used on the GUI role at project save and load. **Memory:** stock heap lock+allocate+unlock returning null instead of the fatal reporter (`sample_cache_stock.cpp:65-71`); plain stock exhaustion is fatal (`docs/builder.md:211-213`).
- **Control points:** synth initializer exit (both roles) and screen factory exits (GUI) at boot; `load_project`'s `deserialize` hook (`0x8d58913e`), for the workspace at startup and each project opened, into the *inactive* buffer before it becomes pending (`abi:850-864`); project save; catalog insertion (`extensions_catalog_checked`); preset scan; factory per note and render per 64-sample block (audio role); extension events on the controller path (`docs/extensions.md:62-66`). The core is a single BF707 (`-mcpu=bf707`, `tooling/native.py:54`); "roles" are stock tasks [I].
- **The hook to load at:** a project names each pattern's engine at pattern `+0x18` (`abi:866-870`), so the deserialize hook can list the machines a project needs before any note reaches them.
## 3. Loading points
| Point | Hook exists | File access | User sees | Risk |
|---|---|---|---|---|
| Boot, all installed (synth initializer exit) | yes | [U] filesystem ready? | catalog 9.5 MB at ~2 MB/s: ~5 s more boot [I] | same limit as today; no gain |

## 4. Memory
- **Not the heap.** Stock heap exhaustion is fatal, samples share it, and the 4 MiB option already warns of instability (`builder.md:211-213`). Heap code may also be out of reach: the heap spans about `0x8c0d0380-0x8d2d0380` (20 MiB ending at `RESERVATION_END`, `stock_tables.py:68`), and a Blackfin CALL reaches ±16 MiB (our type 9/10 check, `native/mod_link.cpp:975-978`), so its low part cannot call stock code at `0x8d50xxxx` without veneers [I]. Free heap at run time is [U].
- **A reserved arena works:** keep today's 2/4 MiB reservation; the base (SDK, services, runtime, extensions, stub table) takes its bottom, the arena the rest. Benefit holds: install all 82 packages (9.5 MB on disk; code 2.4, data 4.5, state 2.8 MB), pay only for what one project uses. State (voice pools, BSS) is loaded memory too (`docs/api.md:38-47`).
## 5. Unloading
Stock keeps handles from earlier factory calls, and when it drops them after a project switch is [U]. **v1: never unload until reboot**; a boot loads only the workspace's machines. Cost: switching between unlike projects fills the arena; when a machine no longer fits it stays silent and the user is told to restart. Freeing needs a point after the new buffer goes live and stock released the old objects (Q4).
## 6. Shared services, runtime, and which package types can be loaded
- **Services and runtime stay in the image.** A service carries service-gated stock edits and fallbacks (`resolve_edits`, `native/mod_patch.cpp:365`; record 028 §1); edits are patched code, not loadable data. Linking all services always costs ≤235 KB (samples alone 145 KB, mostly BSS); runtime members (divide, memset) are tiny. Then gated edits are always on: they must be transparent without a user [U, Q6].
- **synth, effect:** loadable (record + factory; an effect's state lives in the stock 476-byte FX slot, `api.md:56`). **sample, drum:** bodies loadable, with their services in the base. **Own-screen machines:** need late screen registration (§1) or their screen object kept in the base. **player:** generated tables and hooks (`player_table.cpp.in`, `player_hooks.s`); our layout reader rejects players today: later.
- **Extensions:** no extension patches the firmware; every site belongs to the SDK's `extensions` and `master_filter` services (`docs/extensions.md:18-21`, `abi:1977-1990`). An extension is reached through a generated `ExtensionEntry{id, claims, actions, Hooks*}` table (`sdk/platform/extension_runtime.hpp:14-18`), so its body *could* be loaded at boot behind a stub. But claims (`ext-capture`: `record_double_tap`) are resolved per build, and `ext-master_dj_filter` runs a processor in the master audio path, so boot only, never at project load. Both are small (capture 8 KB, dj filter 36 KB). **Keep extensions built in**: then changing the extension set still rebuilds the base image (only the base: no machine objects, so seconds). It would not, only if both services are always linked with their edits transparent when unused (Q6) and claims move to boot.
## 7. The loader
- **In the OS (Open-XY runtime), small:** read a per-machine file, check it, copy into an arena slice, apply relocations, flush data cache and invalidate instruction cache for the range ([U]: does stock have such a routine, Q5), fill the machine's slot, then the stub answers "ready". ~1-2 KB [I].
- **`native/mod_link` does not go into the OS** (51 KB, needs a 5.5-7.4 MiB workspace, record 028 §7). It stays in XY Forever as the **install-time preparer**: imports are only SDK, stock and number symbols, never another package (`foreign_import`, `mod_link.cpp:957`), so with the base pinned every import resolves at install time. The output per machine: initialized bytes linked at offset 0, BSS size, and a compact list of words to fix: type 18 (word) and 6/7 (half-words) add the load address; 9/10 (CALL/JUMP to base or stock) are recomputed from the load address (`mod_link.cpp:966-982`: our only four kinds).
## 8. Who builds what; questions for the Open-XY maintainers
- **Open-XY:** slot-table startup independent of the collection (stub records, silent handle), the loader in the deserialize hook, late screen registration, services always linked, the loadable format accepted by their builder too (else `recoverFirmware`, `builder/core.mjs:1060`, rejects it).
- **XY Forever:** the per-machine loadable files at install, the on-disk layout (STORAGE: a `loaded/` folder per base), numbers for all installed machines, base rebuild on install of a service or extension, Mods page.
- **Q1** When does the synth initializer run again, and is the filesystem usable there? **Q2** Is there a GUI-role point where a track's engine is set from a catalog/preset choice, before its first factory call? **Q3** Startup order: workspace `load_project` vs synth initializer vs screen factory; can a screen register later? **Q4** When does stock release a machine's handles after a project switch? **Q5** Cache maintenance routine and DDR cache mode? **Q6** Are the gated edits of `samples`, `drums`, `extensions`, `master_filter` transparent with no user, so they can be always on? **Q7** Would they adopt a loadable format, or is this XY Forever-only?
## 9. Recommendation and steps (one builder each)
**A first experiment, not a build item yet.** Smallest proof: `sift` (synth, 32.6 KB, no own screen, no service) loaded from disk at project load, the rest linked as today.
1. **Orchestrator:** send §8 Q1-Q4 to the maintainers; stop if Q2 has no answer and the menu path cannot be found (then the only gain is project-scoped loading).
2. **XY Forever, host only:** `mod_link` writes one machine's loadable at a fixed arena address; host test: equal to a full link placing it there.
3. **Test-only SDK fork** (private, from `ba943a8`, never shipped; or the maintainers): `sift`'s record served by a base stub; in the deserialize hook, if a pattern uses `sift`'s number, read the file into the fixed slice, flush caches, publish. One log line to a file.
4. **Device (user boots the test entry):** workspace with `sift` on track 1 plays; a project without it loads nothing; with the file removed, `sift` is silent and nothing crashes.
5. Then the relocatable list (§7) and the arena allocator; decide go on Q2/Q4.
**Plans.** Selection Saves disappear (everything installed is registered): #27 steps D (pinned placement/edit) and B (other slot as cache) become unnecessary; content by difference still serves install/remove and should go ahead now, since this is months away. The meter becomes per project (loaded vs arena); the 64-machine limit is our reader's (`docs/storage/mods.md`, `layout.json`), stock room is 223 more engines and 44 effects. The content switch runs only on install/remove.
**Not known:** Q1-Q7; free heap at run time; read speed of stock `fread`; how many machines have own screens that must register late.
