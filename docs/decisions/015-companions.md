# 015: Companion chips: what they are, how stock updates them, what is recoverable

Research record, 2026-11-14; no device, nothing built or written. **[L]** read from the 1.2.1 bootloader listing (the private `analysis/bootloader-121-listing`) or OS strings, **[M]** measured on files in the private folder, **[I]** inferred, **[U]** unknown, **[D]** design choice. Prior evidence (re-checked where cited): the maintainer's (not shared).

## Answer

The Bluetooth application can be updated in a way that is recoverable without external hardware, by our own updater over raw UART calls (option b). **The backplane cannot be shown to be recoverable with the evidence we have: a failed backplane update may need a debug probe.** Order: the read-only inventory first, then BLE. The backplane stays unsupported until unknowns (1) and (2) below are settled.

## The chips

- **Backplane/keyboard: Cypress PSoC**, silicon ID `0x100A11A0` rev 0 [M]. B talks to it over UART0 at 1 Mbaud (`88a24864` opens "PSOC" with `11a049aa`), with TE framing (COBS + CRC-8) and handler object `0x88a522c8` [L]. It owns the keys (request 0x41, reply at `0x8807ce7e`), battery and charge (0x36/0x37), power modes (0x30/0x31: active, standby, off, charging; it wakes the Blackfin to charge), the USB current limit (0x33/0x34) and the USB-C role [L strings, usb-vbus-001].
- **Bluetooth: Nordic nRF** (Cortex-M application, Zephyr strings) with TE's DFU bootloader in two slot images [M]. On B, UART `0x20087000`, handler `0x88a3e014`. It is opened only on the stay-in-bootloader path (`88a35d4c`) and by the updater, not on a normal boot [L]. It does BLE MIDI [I]. **A silent BLE chip** does not affect boot, keys or XY Forever [I, high].
- **A silent PSoC [L]:** the link open `88a24864` greets it; if that fails, it logs "psoc might be stuck in bootloader, try to exit", sends Cypress Exit (`88a26f5e`), waits 1.5 s and goes on. The key check `88a20852` (one 0x41 request, 100 ms limit) logs "no keys from psoc" and returns 1. Main (`88a357a0`) treats that as held ("bootloader held, stay in bootloader!") and never loads the NAND `os.ldr`. **So while the PSoC is silent, XY Forever, the OS and hold-COM all fail** (COM is read the same way). The stock menu ("1. upload firmware … 3. dev menu") is driven by keys [L strings, I]. `wait_for_battery` `88a1dbae` also polls the PSoC; with no reply it probably leaves after ~3 s through the local current-limit fallback `88a1c91a` [I]. The stock boot logs in 25 of our device reports (tests 017–044, `075/`) show the PSoC always greeting at once ("[key status] bootloader: 0", no "stuck" line) [M].

## What the packages carry [M]

Backplane `backplane/bin/backplane.cyacd`, 193,423 B in all three: 1.0.5 in 1.1.33+1 (`19566682a442…`), 1.0.7 in 1.2.1 (`2a7f21819abc…`), 1.0.8 in 1.2.5 (`d2ab1077ba15…`). BLE application `ble/bin/ble.bin`: 1.0.1, 244,280 B (`74549ae976b6…`), the same bytes in 1.1.33 and 1.2.1; 1.0.2, 244,816 B (`5a713c93a5e5…`) in 1.2.5. Nordic bootloader `nordic_bootloader_{0,1}.bin`, 11,736 B each, 1000.0.10: identical in all three (`96cd41ca6b94…` / `301a8a3acf6d…`). `blackfin/bin/bootloader.version` (text only): 1000.0.20, 1000.0.20, 1000.0.23.
The CYACD header is `100A11A00000`: 367 rows of 256 B in array 0, rows 25–390, then row 511 last. Rows 0–24 (6.25 KB, the PSoC's own bootloader) are in no package, so its behaviour cannot be read offline. 1.2.1 → 1.2.5 changes 362 rows.

## How stock 1.2.1 updates them [L]

- **Only from the update orchestrator** `88a2863c` on B, after a signed `.tfw` upload in update mode or on a resume (SPI marker `0xab0d`). Order: content, os, bootloader, ble `88a2742c`, ble bootloader `88a2756e`, backplane `88a26f90`, spiboot. It sets the marker first and writes each component's version to SPI after success (`11a05312`). A failed handler leaves the marker, so the next boot resumes. **When it programs:** it compares the package version with the version recorded in SPI (`0x11b012b8` BLE, `0x11b012c0` BLE bootloader, `0x11b012c8` backplane) as four 16-bit fields (`11a078d2` via `88a267ba`). Equal: skip. Any difference, newer or older: program. The chip itself is never asked. A force flag `0x88a291c3` bypasses the gate (package version 0.1.0, one upload path).
- **Backplane** `88a26f90`: (1) empty image: skip, then the version gate; (2) enter the PSoC bootloader (`88a26e7e`, 3 tries): TE message 0xee to the application, handler to RAW, wait 250 ms, then a raw Cypress Enter-Bootloader carrying a 6-byte key stored at `0x88a290ac` (`88a267e8`; this also works on a chip already in its bootloader: "backplane seems to be in bootloader mode"); (3) write `tmp/psoc.cyacd` to yaffs through stock stdio; (4) program with the L1 Cypress host library `11a09582`, up to 3 attempts: silicon-ID check, then each row programmed and checksummed ("expected device does not match", "flash row is not valid"); (5) poll `88a24922` every 10 ms for the application's greeting, send Exit from 1 s on, give up at 2 s. Failure returns 1. `88a26a80` only prints the error: HARDWARE.md's "Cypress rows" label for it is wrong.
- **BLE** `88a2742c`: version gate, then the transfer `88a27278`. The transfer needs the chip in DFU (IsInDfu `88a21b22` reads the metadata "mode"), prepares it, sends 248-B chunks and compares the Nordic's CRC-16 ("CRC incorrect"). The orchestrator enters DFU (`88a23a28`) and leaves it (`88a2366a`). The BLE bootloader handler `88a2756e` sends the slot the Nordic asks for (`88a2374c`).
- **Not a driver layer:** the poll `88a24922` hands PSoC messages to the generic dispatcher `88a21456`, which has a conditional path to the SPI metadata writer (TFW-AUTH §3). **1.2.5 bootloader:** the same version-gated handler structure (`boot125-osinstall-safety-001/companion-update-findings.json`); no companion change was found; it was not re-read here.

## What the OS versions need

Neither OS contains companion-programming code or a companion-version check; their companion strings are the same apart from source paths [L]. 003 Q5 holds for the companions: a booted OS cannot program one; it can only reboot into stock update mode when a host asks. 1.2.5 ran on 1.0.7/1.0.1 in Test 053 and in a community report [M, shallow]. A mismatch costs the companion fixes (1.2.5 notes: BLE MIDI with WIDI and recent macOS; the backplane change is unknown) [I]. Nothing is known to break [U].

## Recoverability

- **BLE application [I, medium-high]:** a cut or rejected transfer leaves the Nordic bootloader in DFU. We never write that bootloader. The device still boots, the keys work and XY Forever can retry. A stock reinstall would not repair it: SPI still records 1.0.1, so the gate skips BLE. Unknown [U]: does the Nordic bootloader stay in DFU by itself when the application is invalid (stock always enters DFU through the application, 0xee)? Is a downgrade accepted? Wrong-image guard: the platform word in TE's header (product 0x21 + hardware revision; native notes).
- **Backplane: may need external hardware.** A cut mid-program most likely leaves the PSoC in its own bootloader: rows 0–24 are never written and row 511 goes last [I]. Then there is no key reply, and XY Forever, hold-COM and the OS are all out of reach [L]. A software recovery needs all three of: (1) **[U]** the Blackfin powered at a cold start while the PSoC sits in its bootloader (the PSoC runs the power modes, and its bootloader code is not available); (2) **[U]** the stock update disk reachable with no key press on this dev-marked device; (3) an official package whose backplane version differs from the SPI record and whose bootloader is 1000.0.20: that is 1.1.33, backplane 1.0.5 [M versions; I that it installs]. 1.1.33 also replaces XY Forever with OS 1.1.33; XY Forever can be reinstalled from the dev menu once the keys work again. The 1.2.5 package would also install its own bootloader: forbidden, and permanent. If any of the three fails, only an SWD probe on the PSoC helps. A wrong image is refused by the silicon-ID check [L strings].
- **What a device check without a write can settle:** observation **O1**: power on holding COM with USB connected to a Mac, and see whether a disk appears without any further key press. That answers (2). No such check settles (1): that needs TE, a schematic or a look at the board.
- **Unproven, and corrections:** Unknown [U], besides the items marked above: whether the PSoC answers normal-mode metadata (CP001 assumed it does), and the device's hardware revision. SAFETY recovery step 3 says an official 1.2.1 install "may rewrite the companions": that holds only when the SPI record differs from the package. GOALS says companions "use the stock update routines": that conflicts with rejecting option (a).

## Options

- **(a) Stock routines: rejected.** `88a26f90`/`88a2742c` are stock features: they use the SPI gate, yaffs stdio, the dispatcher with its SPI-writer path, and leave DFU entry to the orchestrator. No subset of them is a driver layer.
- **(b) Our own updater over raw UART: recommended.** It uses CP001's 4 calls (open `11a049aa`, write `11a04b42`, read `11a04b88`, close `11a04c80`), the native `companions`/`ble_session`, and our own bounded loops on B. The image is staged and hashed in B's RAM before any traffic, so B never waits on A during a transfer. It fits the Shape rule. Cost [I]: about 600–900 lines plus simulator models.
- **(c) Stock update mode: not viable.** The 1.2.1 package changes no companion on this device, because the SPI record matches [I]. The 1.2.5 package also flashes its bootloader and replaces XY Forever, so the dev menu and XY Forever are lost for good. **(d) Nothing:** 1.2.5 runs without the companion fixes; this is the backplane default.
- **What (b) needs from the builder:** allow the 4 UART calls, and only in the companion feature. Every current forbidden target stays; add `11a09582 88a26e7e 88a26f5e 88a23a28 88a2366a 88a2374c 88a2383e 11a07412`. Read the key from `0x88a290ac` at run time; never copy it into git.
- **Checks around every write [D]:** the image's SHA-256 equals an official member above, inside a signature-checked `.tfw` (003); the silicon ID or BLE platform word, and the hardware revision, match; battery ≥ 50 % and USB power present; confirmed on the device; a journal in `/yaffs2/xy-forever/` written before DFU; the guard fed, and nothing resets or ends the session during a transfer; never the Nordic bootloader slots.

## Staged path

0, offline: re-derive the protocols from 1.2.1 (the native code came from the 1.2.5 listing); simulator chips with a cut at every row and chunk. Worst case: none. 1, read: SPI-recorded versions in RAM (`0x11b012a8..0x11b012d0`) and a handler snapshot. Worst case: B hangs; guard or power cycle; recoverable. 2, normal-mode metadata over raw UART, as CP001. Worst case: as stage 1. 3, mode change, no write (user's yes): BLE DFU enter, metadata, exit; PSoC Enter, flash size, verify checksum, Exit, with the application intact. Worst case: a chip left in its bootloader with a valid application; stock sends Exit every boot [L]; recoverable [I]. 4, first write (user's yes): BLE application 1.0.1 → 1.0.2. Worst case: BLE off until XY Forever retries; recoverable [I]. 5, backplane write: only once O1 is yes and (1) is settled. Worst case today: an external probe.

## Earlier preparation

- **`native/companions`, `ble_session`, `xy_forever/companions.py` (40 tests):** host-only codecs (Cypress packets and row session; BLE header, chunks, CRC and response-driven session). No transport, no recovery. Derived from the 1.2.5 listing.
- **Earlier companion prep (the maintainer's archive, not shared):** one commit on build 116, never merged. It holds CP001: an on-demand normal-mode metadata probe (`target/companion_probe.cpp`: the 4 raw UART calls, a COBS/CRC codec checked against the stock table, guard required, 300 ms limit), a host runner, an audit, with the whole suite (459 tests) passing then. Never run on a device. Still valid: the addresses, the codec and its tests, the audit excerpts. Stale: the build wiring, the protocol opcode, the 090/116 kit. **Port the codec, tests and audit into stages 1–2; do not merge the commit.**
