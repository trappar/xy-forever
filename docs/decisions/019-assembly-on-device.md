# 019: Where mod assembly runs on the device (plan item 5.4r)

Research record, 2026-11-14, against build 158's map, the 5.4a package set (the private `paths.PUBLISHED_MODS`), open-xy `core.mjs` at `52c8de9`, device evidence from device pass 4, qualification run 085 and build 069's report (the maintainer's, not shared). No device, no build. **[C]** read from code/docs, **[L]** stock listing, **[M]** measured, **[I]** inferred, **[U]** unknown.

**Question:** which processor links and patches, with what memory, how inputs and outputs move within the shape rule, how long Apply takes, what a power cut leaves, and how 5.4d splits.
## Answer in brief
**On A, as one file-engine job; B drives it and shows progress.** A owns every input and output file, so nothing crosses the link but requests and a status record; B keeps every decision (target id, commit, boot once) through the engine it already uses. Working memory: the 8 MiB region `0x8b000000..0x8b800000` on A, empty in the product; peak ≈ 6 MiB. Apply ≈ 4.5 s (1 machine), 5.5 s (7), 8.5 s (16), dominated by the unmeasured yaffs write speed. No new stock call. Two premises corrected: the assembled `os.ldr` is up to **4,454,120 B** (stock 2,373,336 + 16-byte record + module ≤ 2,080,768 before FINAL, `patchFirmware` [C]), not ~2.4 MB; and 175 KiB/s is the USB rate, not the link's (§2).

## 2. A or B
- **Traffic** [M/I]: Apply moves 8-17 MB (objects twice, stock, the output, its read-back). On A that is local: A read 2,373,336 B in 134 ms (q-085) to 487 ms (HARDWARE), 4.9-17.7 MB/s. On B every byte crosses the link: bulk image transfer ran ≥ 1.8 MB/s (q-085: metadata at 914 ms, all received and hashed by 2,185 ms), so +4-9 s; through the file engine (1 KiB requests) the link speed is **unmeasured**: a 1 KiB ranged read (5 link requests) takes 5.6 ms, the same as a USB-only 1 KiB `stage.data`, and HELLO takes 5.05 ms [M pass-4], so 172-176 KiB/s is the USB limit. At that floor B would add 50-100 s.
- **Shape**: 009 already puts A-local work (hash job, commit) on A with direct yaffs calls; assembly is the same kind of job. B's UI needs only a status record. A split (B links, A patches) moves the 2 MB module across the link and buys nothing.
- **Code** is the same either way: one image runs on both processors.
## 3. The job (A) and the shape rule
- **Flow** [I]: B writes `tmp/<job>/job.txt` (selection, target id, generation) and makes the folders through the engine, then starts job `assemble`. A, each file read whole with direct yaffs open/read/close (no lseek on A): base tables (edits.bin 8,888 B, objects.txt, absent.txt, …) → stock `os.ldr` into the image buffer, SHA-256 = `needs_os` → pass 1 per object (headers, symbols; numbering, placement) → pass 2 per object (bytes + relocations straight into the image buffer at `stock_bytes`, per-file SHA-256 against `files.sha256`) → edits, record, first header, restore check, `ldr::inspect` → stream-write `os.ldr`, `layout.json`, `content/op1_factory.json` (≤ 16 KiB [I]; official 5,501 B), svgs and presets copied, `files.sha256`, `info.txt` last → read back each file, SHA-256 + CRC-32.
- **Peak memory** [I]: A = image buffer 4,454,120 B + one object ≤ 1 MiB (largest `troupe/voice.o` 896,192 B [M]) + link tables ≤ 512 KiB + 64 KiB I/O ≈ 6.0 MiB of 8. B = nothing new (one status body).
- **Bounded** [I]: the job runs in slices from A's poll loop: one object step, one edit pass or one I/O chunk (start 16 KiB; set by the yaffs write pause, §8), so A serves B's requests between slices and reloads its guard; the long guard count stays only around window open and close, as today. B polls `job.status` (query class, 5 s bound) every ≤ 250 ms, which also keeps A's 25 s alone rule satisfied; its own guard kicks in that wait loop. The window stays open while the job runs (the job counts as an engine item).
- **Cancel, faults**: `job.cancel` sets a flag A checks each slice; A closes its two handles; B deletes `tmp/<job>/` (or the next sweep does). B silent 10 s: A aborts the same way. Link lost (60 s): B shows it; the debris is swept at the next start (010). Progress: {phase, done, total, status, detail} to B's screen and as 004's `job.status`/`progress`.

## 5. Storage, write order, power cuts
- **Space**: inputs stay; new: ≤ 4.46 MB `os.ldr` + ≤ 1.1 MB content + lists ≈ 5.6 MB in `tmp/`, and the old target until its delete. Free space minus 010's reserve is checked before the first write. Steady state: two mod sets + the cache (12.5 MB [M]).
- **Order** (B drives; only `tmp/<job>/`, the target id and the device layout are ever written): (1) preflight, read-only: target = the mods id that is neither `default` nor `once` (neither is the default: the absent one, else the older); `needs_os` = the stock entry's `sha256`; space. (2) folders + `job.txt`. (3) A's job writes and reads back. (4) `mods/<profile>/layout.json` via `tmp/` + rename, **before** the commit (change to 008: numbers only grow, so a cut leaves one extra held number, never an entry whose numbers are not held). (5) rename the old target into `tmp/<job>-old`, rename `tmp/<job>` onto the target, delete the old tree. (6) CHECK of the new entry, then the boot-once offer (slot write `once=`; its content needs 4.6c's switch first, 018).
- **Cut** at (1)-(3): `tmp/` debris, swept at the next menu/USB start; no read-write checkpoint, so one slow mount (4.5-17 s). At (4): an extra held number. Between the renames of (5): the target id is missing until Apply runs again; nothing else changed. After (5): the entry is listed and can be booted once from the menu. (6): proven A/B slots. Apply needs no journal; the default entry and the other mods id are outside the write set (a pure `decide_apply` on A and B, as `decide_engine`).
## 6. Verification before the entry is admitted
- In RAM before any write: inputs (generation, `needs_os`, per-file SHA-256); every `linkKit` check (opcode, ±16 MiB, duplicates, unresolved, overflow, 2032 KiB); every `patchFirmware` check (preimage and mapping per edit, overlaps, hooks inside the module, reservation covered by the stock zero-fill, FINAL unchanged, restore = stock SHA-256); `ldr::inspect` with the cold policy, entry `0x11a00000` (module at `0x8d2d0380..0x8d4cc380` is allowed, below the reporter). After the write: read-back SHA-256 + CRC-32 per file, strict `info.txt`, then the boot-time CHECK on the committed entry.
- Host: the entry keeps `layout.json` (selected, numbers, extensions), `generation`/`needs_os`/`profile`, and `inputs.sha256` (new, shasum format: every package file it used). `xyf_host.py mods verify <id>` re-links on the host (`core.mjs` and the host-compiled native code), compares SHA-256 with A's hash job, and in 5.4f pulls the whole `os.ldr` (~26 s at 172 KiB/s [M]).
## 7. Constraints for 5.4b and 5.4c (the interfaces)
1. **Inputs are whole files in RAM**: A has no seek (direct yaffs lseek is not on the allowlist; adding it is a new stock call). The linker takes one object at a time as (pointer, size) ≤ 1 MiB, in link order, at most two passes; nothing may point into an earlier object's bytes; what pass 2 needs lives in its own bounded tables (bound stated for the whole kit: 395 objects, 2,893 globals, 53,953 relocations). A `Reader` may stay if every read falls inside the current file (the device backs it with that RAM copy).
2. **Outputs into caller buffers, not writers**: the patcher works in place on a caller-owned image buffer (capacity stock + 16 + 2,080,768); the linker writes the module straight into it at offset `stock_bytes` (before FINAL), so there is no second 2 MB copy. Layout and catalog go to buffers with stated capacities; svgs and presets are copied by the job, so 5.4c only lists them. If a writer is kept: append only, one file at a time, any chunk size, a false return stops cleanly.
3. **Steps**: an API in steps of at most one object (place, relocate) or one pass over the edits; hashing through incremental `native/hash`; no step over ~50 ms at 400 MHz for the largest object [I].
4. **Freestanding as the product**: no heap, no BSS, no memcpy, memset or division helpers (`test_xyf_freestanding`, `module.ld`); workspace sizes as functions of limits (as `tfw_os::scratch_bytes`), 4-byte aligned; no recursion, small frames (the cold stack is 16 KiB for everything [C]).
5. **Report the Blackfin text + rodata size.** Build 158 has 24,248 B free [M]; at 9-15 B per line (ldr, hash, file_engine, storage_server in 158's map [M]), 5.4b + 5.4c (~1,000 lines) ≈ 9-15 KB, and 5.4d/5.4e need more [I].
6. **Errors** as a code plus a ≤ 32-byte detail (object, relocation or edit index) for `job.status`. `layout.json` output must fit our reader (8 KiB, 64 machines [C STORAGE]) or the reader grows with it.
