# 028: Saves that converge (#27, research)

Research record, 2026-11-15; read-only, no device action. Open-XY facts from a fresh upstream clone (`paths.OPEN_XY_UPSTREAM`) at **`ba943a8`** (`builder/core.mjs`); our linker ports `52c8de9`. Packages: the published 0.0.6 set (`paths.PUBLISHED_MODS`). Timings: the first mods-apply session (builds 172-173) and two device passes' apply and switch steps (the maintainer's, not shared). Tags: **[C]** our code, **[O]** open-xy, **[M]** measured, **[I]** inferred, **[U]** unknown.
**In brief.** An image *can* be edited: every tie between a mod and the image can be listed in a manifest. But a power-cut-safe edit still writes the whole `os.ldr` (yaffs gives us no cheap copy). So editing saves only the package reads and the link: about 4 s of an estimated 35-70 s Save with 30 mods. For remove-one, the larger costs are probably per file: ~140 content files written into the new entry, the old entry's files removed at the commit, and the content switch copying every file again. **Recommendation:** measure first. Then make the content switch converge (write only what differs). Then let the other slot act as a cache. Build the edited image (placement as an input plus a manifest) only if the measurement still shows link and reads as a large share. Steps in §9.
## 1. Every place a mod is tied into the image
- **Its own bytes are in up to four ranges, not one.** `place()` (`native/mod_link.cpp:711`, = `linkKit` `core.mjs:765` [O]) lays out every linked object's sections group by group: all text, then rodata, data, bss. A machine has one range per group. Kit order puts all machines (orders 0-323) **before** the SDK (324-394) [C `base/objects.txt`]. With the default (packed) placement, removing `fm2op` (order 0) moves every later section, so every relocation changes. The edit idea needs placement as an input. A removal can still leave a hole and move nothing else.
- **SDK → machine.** Three SDK objects import each machine's callbacks and numbers: `startup.o`, `benchmark.o`, `project_companion_table.o`. That is 19 relocation sites for `fm2op` (11 + 6 + 2 of 2,398) [M objdump]. An unselected machine's callbacks resolve to `kit_absent` (`absent.txt`, 426 rows, about 5 per machine). Its `<prefix>_engine_id/_page_id/_screen_page_id` symbols are 0 (`number_symbols`, `mod_link.cpp:762`; `aliases`, `:794`). Removing a machine means re-pointing those sites.
- **Machine → anything.** Machines import only SDK, stock (`definitions.txt`) and number symbols. A package object importing another package's symbol is refused (`foreign_import`, `pass2` `:918`) [C], so **no references between mods**. With the SDK pinned, a mod's relocated bytes depend only on its own address.
- **Shared services** (`base/services.txt`): 13 machines use them; `samples` alone is 145 KB, and samples + drums + octaves + drum_sends + drum_locks is 235 KB, mostly bss. A service has no owner. It is active while any selected machine (or extension) lists it (`prepare` `:539`). Only the last user's removal frees it. Then three things change: its objects go, its fallbacks (`fallbacks.txt`, 12 rows) are re-pointed in the SDK, and the service-gated **stock edits** switch off (`resolve_edits`, `mod_patch.cpp:365`). That last change rewrites bytes in the stock part of the file.
- **Runtime members** (`runtime_closure` `:662`, `selectRuntime` `core.mjs:715`): added while any linked object has a pending import. The set can shrink when a mod goes.
- **Hooks** (205 edits in `edits.bin`): they target SDK or service symbols only, never a machine's symbol [M strings]. With the SDK pinned they stay fixed, except for the service gating above.
- **Derived from the whole selection:** the module's record count, the first record's length and their XOR bytes (§2); `layout.json` (`selected`, `machines` numbers; `numbers::layout` keeps earlier numbers when given the device layout [C], so the other mods' numbers and catalog entries stay put); `content/op1_factory.json` (the official file with each machine's `catalog.txt` inserted at three pinned offsets, `mod_content.hpp`); `files.sha256`; `info.txt` `bytes/crc32/sha256`; `config.txt` `built`/`stamp`. The heap edits depend only on standard or expanded memory, not on the selection.
- **Content:** each mod's svg and presets (6 files on average). An aux preset path that two machines both carry is listed once, with the later machine's copy (`mod_content.hpp`).
## 2. The image container (`os.ldr` as we write it)
- Layout: stock 1.2.1 (984 loader records), the edits applied in place at fixed file offsets, then the module record replacing FINAL at `stock_bytes-16`, the module (initialized bytes only), then FINAL (`apply_edits`, `mod_patch.cpp:388`). Checksums: **each 16-byte header has an XOR byte, and nothing else does**. Payloads have no CRC (`header` `:38`). Lengths: the module record's `count` and the first record's `argument` (= total − 16). Whole-file SHA-256 and CRC-32 exist only in `info.txt`, `files.sha256` and `config.txt`.
- A range inside the module can be rewritten without moving anything after it. A size change moves only FINAL (16 B) and two header words.
- **bss is free:** a stock zero-fill record covers the whole reservation before the module record loads (`core.mjs:922` [O]). So bss may sit anywhere outside the initialized range. Added initialized bytes cannot go after `data`, because bss starts there. Either they go into holes, or the layout keeps a gap (initialized from the bottom, bss from the top). A second module record is possible for the loader [I], but `start_verify` and open-xy's `recoverFirmware` expect one.
- **File level:** the job's file table has no seek (`mod_job.hpp` `Files`). B's client has `seek` (op 0x2c, `file_client.hpp:94`), and A's engine accepts a write open and lseek (`file_engine.hpp:47,83`). An in-place write into an existing yaffs file is **never tried on the device** [U]. Rewriting `os.ldr` in place in a live slot is not power-cut safe. On a copy it buys nothing, because the copy already writes every byte.
## 3. Operations under a free-range scheme (manifest: every object's sections, addresses; the SDK sites of §1; active services, runtime set; image SHA-256)
Reference: **30 small machines** that fit standard memory (§8 list): image ~3.2 MB, objects 1.07 MB, content 0.68 MB in 138 files. A typical 30 needs expanded memory: image ~3.9 MB, objects 1.9 MB, content 1.1 MB in 219 files [M package sizes].
| | Edits | Package bytes read | Image bytes written |
|---|---|---|---|
| Full build (today) | everything | ~6.0 MB (stock 2.37 + objects twice 2.8 + content 0.7) | 3.2 MB + 0.7 MB content, 143 files |
| Remove-one | hole (zeroed, avg 85 KB); 19 SDK sites → `kit_absent`/0; if last user: its service's objects, fallbacks, gated stock edits; runtime set; catalog, layout, lists | old image 3.2 + manifest ~50 KB + `edits.bin` 9 KB + 29 `catalog.txt` | 3.2 MB (whole copy) + 134 content files copied from the old slot |
| Add-one | first fit for its four groups (bss from the gap), else compact; its objects relocated; its 19 SDK sites; service + fallbacks + gated edits if new; runtime members; number from `numbers::layout` | old image + its package ~0.2 MB + SDK globals (manifest, or base objects 0.39 MB) | 3.2 MB + content |
| Replace-one | remove + add (same range when it fits) | as add | 3.2 MB + content |
| Compact | full build | as full | as full |
A first fit almost never succeeds right after a packed full build, because there are no holes and no gap. Add-one only helps after removes, or once full builds leave a gap (a non-default placement).
## 4. Where a Save's time goes
Measured [M]: 1 machine job 8.4 s (0-1.0 s inputs and stock read through B's client, ~2.3 MB/s; link 1.5-2.6; patch 2.6-4.3; write 4.3-5.3; verify and finish 5.3-8.4; wall 8.9 s with the commit). 7 machines (3,086,632 B, 23 files): 11.5 s (link 1.6-4.2, patch 4.2-5.8, write 5.8-7.3, verify 7.3-11.1, renames 11.1-11.5). Phase boundaries are ±0.5 s, because the host polls every 0.5 s (`modsend.wait`). Content switch, fm2op (3 files): 0.6 s of work + 0.6-0.8 s window close. Window close after writes: 0.3-17 s. **No Save with more than 7 mods has been timed.**
Fitted guess for 30 small [I]: stock 1.1 s; link ~1.5 s/MB of object reads → ~4 s; patch ~0.55 s/MB of image → ~2 s; write + verify + renames ~1.55 s/MB + ~0.03 s per file → ~10 s; **job ~17 s**. Unknown [U]: the commit's removal of the old 30-mod tree (~140 unlinks, one per loop pass); the window close; the content switch, ~0.1-0.2 s per file → 14-28 s; the record. **Save ~35-70 s.**
## 5. Content files
The switch removes by difference: only previous files the target lacks (`st_remove`, `xyf_content_job.hpp:478`). But it **copies every target file**, even unchanged ones: load, write `.part`, read back, unlink, rename (`st_copy` `:503`). `content-state.txt` keeps paths only, no hashes. Minimum for remove-one: unlink that mod's ~6 files (and its empty folders), rewrite the catalog, and write the record twice (switching, installed). To skip a file safely, read the live file and compare its SHA-256 with the target's line. This is read-only and avoids every change request. Do not trust the previous entry's list: the user or the OS may have touched `content/`.
## 6. Cheaper paths that keep the image byte-identical
- **Other slot as a cache:** `check()` (`xyf_mods_io.cpp:363`) skips the build only for the slot the record names. The other slot holds the previous selection. Its `layout.json` (`selected`, `extensions`), `info.txt` (`generation`, `needs_os`, `sha256`) and the library's usable flag give its `built` text. If that equals the wanted one: no build, only the content switch and the record. One small read; this fully covers undo and toggling back.
- **Base copied on A:** saves the 2.37 MB stock read across the link (~1 s). It needs the stock write path on A, which #24 rejected (audit change). Not worth it.
- **Prepared per-mod pieces:** relocated bytes are valid only at one address. Pass-1 tables per mod save parsing, but pass 2 still reads every object. Small gain [I]. Useful only together with pinned placement.
- **Content by reference** (variant): the entry keeps `files.sha256` but no `content/` copies, and the switch reads from the package folders. This saves ~140 writes per build and ~140 unlinks per commit. It is a STORAGE change: an entry would then depend on its packages staying.
## 7. Risks
- **Fragmentation:** fallback is always the full build, so holes never refuse a selection. The meter keeps showing the packed size, which is what the full build needs, with "gaps" as an optional second number. Compact when the holes exceed a set share, or when nothing fits.
- **Stale manifest:** it carries the image SHA-256, the base (`needs_os`), the generation, the layout and each package's `files.sha256` hash. The edit job hashes the old image while it copies. Any mismatch, missing manifest or parse error falls back to a full build. A package that changed under the same id counts as replace-one or a full build.
- **Power cuts:** content by difference keeps today's record order. A cut leaves `switching`, and the repair converges. The cache adds no write. The edit job writes `tmp/job-<id>` and commits as today (STORAGE "Into the library"), so it behaves identically.
- **Memory and code:** a streaming edit needs less than the 5.5-7.4 MiB a link uses (B's region is 8 MiB − 64 KiB). The assembler tripwire (51,152 of 51,200 B, `tests/test_xyf_freestanding.py:38`) must be raised deliberately. Manifest writer + edit job ~4-8 KB [I].
- **Compatibility:** open-xy's `recoverFirmware` (`core.mjs:1060`) accepts an image only if it can rebuild it byte for byte. An edited image is therefore not recoverable on its website. This is accepted.
## 8. Options
| Option | Gain, remove-one of 30 | Code, device memory | Risk | Test |
|---|---|---|---|---|
| A. Content by difference (read-compare) | most of the switch: est. 14-28 s → 2-4 s | `xyf_content_job.hpp` only; none | low | simulator: unchanged files get no write; a cut at every step converges |
| B. Other slot as cache | whole build + commit when it matches; 0 otherwise | `check()` + one read; none | low | host: matching or stale stamp; the content switch runs only when needed |
| C. Content by reference | ~140 writes + ~140 unlinks per Save | STORAGE + switch + job; none | medium | simulator, STORAGE tests |
| D. Pinned placement + manifest + edit-copy | ~4 s (link + reads) | builder + job ~4-8 KB; less than today | medium: manifest drift | rule below |
| E. In-place edit of the spare | image write too (~2 s) | as D + seek writes | high: untried yaffs path | not proposed |
**Test rule (improved).** (1) The full builder takes an optional placement (section addresses and the included set). Without one, it equals `core.mjs`, as today. (2) The placement holds addresses only, and the included set stays a function of the selection, so remove also drops orphaned services and runtime members. (3) An edited image **and its manifest** equal a full build given the edited manifest's placement. (4) Every edited image passes `start_verify` with its SHA-256. (5) The simulator runs random remove/add/replace sequences with compaction, checking (3) at each step.
## 9. Recommendation and steps (one builder each)
1. **Measure** (orchestrator, device; nothing else changes). Read `config.txt` to confirm `slot=mods-a`, then run twice: `python3 xyf_host.py --timeout 300 mods apply --base opxy-121-stock --generation opxy-1.2.1/0.0.6-370a949e96aa pingpong ringmod grainfield lustre vibe halo omnifilter gentape breadboard papasrapa fm2op drone daath sift halcyon solar tattva hwander matrixy lint acidline mmnois mmsin mmpar mmens wane tandem mmpulse diffusion mmstat --name "Measure 30" --wait`. These are the 30 smallest machines that are not players; our `layout.json` reader rejects players. Record each phase line and the wall time. Run 2's commit removes run 1's 30-mod tree. Only `firmware/mods-b` and `tmp/` are written. `mods-a`, `content/`, `content-state.txt`, `config.txt` and the default stay. Optional, and only with the developer's explicit yes (it changes the installed content for about a minute): `set-default mods-b --yes-write`, then `set-default mods-a --yes-write`. This times the content switch both ways and ends as before. A cut leaves `switching`, which a Save repairs.
2. **A:** the switch reads each live file and skips the write when its SHA-256 matches. Simulator tests.
3. **B:** the other slot as a cache in `check()`. Host tests, then one device Save toggling back.
4. **Decide D on the numbers.** Go ahead if link + stock read are > 25 % of a 30-mod Save after steps 2-3, else close #27. If D: (4a) host builder: placement input and manifest, rule (1)-(3); (4b) remove-one edit on the host, rule (3)-(5); (4c) the device job, streaming copy with substitutions; (4d) add/replace into holes with a gap layout; compact = full build.
5. Consider C separately: it is a separate storage-format decision.
**Unknown:** the per-file cost of content writes, of unlinks and of the commit, which decides between A, C and D; the window-close time after ~4 MB; whether 30 typical mods fit expanded memory on the device (never run).
