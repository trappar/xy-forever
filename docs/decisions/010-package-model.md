# 010: Package model (plan item 4.1)

Research record, 2026-11-14; no device, no build. **[C]** read from code or records, **[D]** design choice, **[U]** unverified. **Question:** one model for official firmware, XY Forever itself, mod packages, assembled mod sets, content and content packs (companion chips named only): kinds, layout, manifest, state, jobs and power cuts, dependencies, host view, space, build order.
## Model in brief [D]
- **The folders are the state.** A package is installed when its folder or file sits at its home and passes its checks. The library scan already works this way [C `xyf_library.cpp`]. No package database: a copy over MTP and an install by a job give the same result. Only two things need a record: what boots (the A/B slots, unchanged) and what XY Forever put into the shared `/yaffs2/content/`.
- **Every add or remove is one rename.** A job builds its result in `tmp/<job>/`, checks it, then renames it onto its home (009's rename on A). A remove renames into `tmp/`, then deletes. A power cut leaves only `tmp/` debris. Only the content switch changes many files in a shared folder, so only it keeps a journal.
- **Content files are kept by hash.** Every file named by a kept content manifest is either at its path in `content/` or in `blobs/<sha256>`. A `.tfw` install stores the content files the device lacks as blobs, so the 98 MB file can be deleted afterwards and any installed version's content is rebuilt without it. This is 006's option b ("cache") with no per-entry copies: 1.1.33 next to 1.2.1 costs ~100 KB [C 006].
- **Kinds** (`type=`): `firmware` (official from a `.tfw`, custom `.ldr`, open-xy builder ZIP via the host, and the mod sets assembled by Apply: two fixed ids per profile, `mods-<profile>-a`/`-b`, Apply writes the one that is not the default, so the other is the way back and no old sets pile up); `mod-base` and `mod` (008); content packs (stock's own `content/dlc/<name>/manifest.json` is their manifest [C 006]; plain folder or content-only `.tfw`); `xyf-stage2` (the 96-byte `XYS2` header is its manifest [C `xyf_stage2.hpp`]); `xyf-stage1` (an XY Forever `os.ldr`, boot partition through the stock writer only, as INSTALL today; menu install decided in 4.7); `companion` (named; the device refuses the type). A content set is not stored as a package: it is a manifest in the firmware entry plus blobs.

## Layout (keeps every existing path; nothing to migrate) [D]
```
/yaffs2/xy-forever/
  state-a.txt, state-b.txt  boot slots, unchanged (default, once, stage2, stage2_previous, stage2_tries) [C]
  firmware/<id>/            entry: info.txt, os.ldr, [layout.json, files.sha256, content.sha256 + firmware.version (its set), content/ (its overlay)]
  mods/<profile>/           layout.json (device numbering, 008) and <generation>/{base,<machine>}/
  blobs/<sha256>            content files a kept manifest names that are not in /yaffs2/content now  [new]
  inbox/                    drop folder for both doors and the menu: .tfw, .ldr, .xys2, package folders [planned]
  tmp/                      uploads (009), job staging, removals; swept when no job runs             [009]
  content.txt, content.list, job.txt   the content record and the content switch's journal (below)  [new]
  settings.txt (4.8), stage2/{main,previous}.xys2 (4.7), log/                                       [planned, C]
```
Outside: `/yaffs2/content/` and `/yaffs2/firmware.version` (written only by the content switch; `content/dlc/` only by pack install/remove); `/yaffs2/layout.json` (read once to seed `mods/<profile>/layout.json`, 008). Never: `bootloader.dev`, `user/`, `/fat32`, `upgrade/`, the boot partition (except `xyf-stage1`), SPI, OTP, companions. Existing devices: an `info.txt` without `type` is a `firmware` entry; entries without `content.sha256` show "content unknown" until the host adds 4.6a's manifest; new folders are made on first use.
## Manifest: `info.txt` key=value [D]
The existing reader [C `xyf_store.cpp`: 4 KiB, values <= 127 B, unknown keys ignored, so older builds still read new files]. JSON rejected: the device has only the layout scanner. Multi-file packages add `files.sha256` in `shasum -a 256` format (`<hex>  <relative path>`, streamed line by line; anyone can make or check it). Dependencies are exact matches only, no ranges.
```
# firmware/opxy-125/info.txt               # mods/opxy-1.2.1/<gen>/fm2op/info.txt (+ files.sha256: objects, svg, presets)
type=firmware                               type=mod
name=OP-XY 1.2.5                            name=FM2OP
version=1.2.5                               version=v0.3.0            (catalog tag; display and equality only)
kind=official                               machine=synth
bytes=<os.ldr size>                         generation=<kit export id>  (must equal the base's)
crc32=<8 hex>        (boot check, as today) source=<repository>@<commit>
sha256=<64 hex>      (what a needs_os names) licence=MIT
content=1.2.5        (content.sha256 holds the set)   # base: type=mod-base, profile=opxy-1.2.1, generation=, needs_os=<stock 1.2.1 sha256>
```
An assembled entry adds `generation=`, `needs_os=` and keeps its selection in `layout.json` `selected` [C 005]. **Before accepting** (any door): path policy (009); known, allowed type; every listed size, SHA-256 and the `os.ldr` CRC-32 + `ldr::inspect` [C]; `.tfw`: 003's checks incl. signature; `.xys2`: header checks [C]; needs met; id free (an install never overwrites); space. Unsigned folders are accepted (user decision): hashes prove integrity, not origin. **A plain copy** into `inbox/` is recognised by shape: `.tfw` magic, LDR (`ldr::inspect`), `XYS2`, a folder with `info.txt` (its `type`), a folder with a stock pack `manifest.json`. Without `files.sha256` the device hashes at install and writes the list into the installed folder; a folder copied straight into `firmware/` works as today.
## Installed state and power cuts [D]
- Boot state stays in the proven A/B slots: stage 1 reads them on every boot and is full, so it cannot learn rename. Every new file is written `tmp/` then rename (simpler, any size).
- `content.list` (`shasum` format: every file XY Forever wrote under `content/`, `dlc/` excluded) is renamed in first, then `content.txt` (`set=1.2.5`, `overlay=<entry id or empty>`, `list=<sha256 of content.list>`). A pair that disagrees means "content unknown": the next switch hashes `content/` instead of trusting the record.
- `job.txt` (`op=activate`, `to=<id>`, `from=<id>`) exists only during a content switch. Repair runs when the menu or USB service starts, never on a plain boot (no writes on boot): sweep `tmp/`; finish a journalled switch (roll forward: the plan is idempotent, files already right are skipped [C `native/content`]), or, if a source is missing, offer to activate `from`. Stage 2 (when it exists) opens the menu instead of booting while `job.txt` exists; stage 1 cannot, so until then a cut mid-switch boots the old default on mixed content (recoverable: PLAY at power-on, finish).
## Jobs (004: one at a time, progress, `job.status`) [D]
- **install** (inbox item): checks above -> build in `tmp/<job>/` (a `.tfw`: entry + `content.sha256` from the ZIP, blobs for content files not already in `content/` or `blobs/`) -> rename blobs into `blobs/` -> rename the entry onto `firmware/<id>` (the commit) -> delete the inbox file. Cut before the commit: debris and unreferenced blobs (collected later); after: installed, inbox file left ("already installed").
- **remove**: not the default or current stage 2; confirmation lists dependents -> rename into `tmp/` -> delete -> collect blobs no kept manifest names. Packs: delete `content/dlc/<name>/`.
- **activate** (set default): same content set and overlay as `content.txt` -> slot write only (today). Else journal -> **content switch** (desired = the entry's set, overlay files win by path; all sources checked before the first write; a replaced or dropped file a kept manifest names is moved to `blobs/`, others deleted; new files copied from `blobs/` or the entry via `tmp/`; `firmware.version` last) -> slot write -> record -> delete journal. Files in no record are left and reported; a full reinstall removes them, as stock (packs kept).
- **apply mods** = 5.4d's assembly into the non-default A/B id (one rename commit), then activate. **switch content / repair** = activate's switch for the current default.

## Dependencies, host view, space
- **Dependencies.** Device, each because a mistake there is made on the device with no host present [D]: (1) `mod.generation == base.generation` and Apply only with an entry whose `sha256` equals the base's `needs_os` (else the assembled OS crashes or cannot be built); (2) a content switch only when every source exists; (3) refused types (`companion`; `bootloader` members, `package_policy::classify` [C]); (4) `XYS2` `min_stage1` [C]; (5) remove lists dependents (`needs_os`) and asks; it does not refuse (recoverable, user rule). Host and web app: which versions exist, compatibility (profile, SDK minimum), updates, downloads, licences. The device never compares versions.
- **Host view.** Queries: `package.list` (inbox items with recognised type, entries, mod cache: id, type, version, sha256, needs), `state.get` (slots, content record, journal), `storage.space` (statfs, A proven [C 009]), `job.status`. Commands (jobs): `package.install`, `package.remove`, `library.set_default` (becomes activate), `mods.apply`, `content.repair`, `job.cancel`; files through `file.*`. Index for 6.1 needs per package: type, id, name, version, file sizes and SHA-256, `needs_os`/`generation`/`profile`, source and licence; `.tfw`: firmware and content versions, SKU; mods: machine kind, catalog id, tag/commit, SDK minimum, cpu and memory size (Apply's 2032 KiB meter).
- **Space.** Measured [C]: `.tfw` ~97.8 MB; `os.ldr` 2.30-2.37 MB; content 125.8 MB / 839 files; 1.1.33 vs 1.2.1 content ~100 KB; whole mod catalog ~8.7 MB; assembled `os.ldr` <= 2.37 MB + 2.03 MB module. Unknown [U]: yaffs size and free space (4.6b), the stock `upgrade/` leftover, write speed. Kept: entries, blobs, mod cache, two assembled sets, two stage 2 files. Deleted: the `.tfw` after install, `tmp/`, unreferenced blobs. Rule: a job adds its worst case (staging + result + blobs) and refuses before the first write if free space minus a reserve is short (reserve size: set after 4.6b) [D].
## Code, unproven, rejected
Kept and extended: library scan, `xyf_store` reader (`info.txt` keys `type sha256 content needs_os generation`), A/B slots, catalog (type in flags), `native/package` + `package_policy` (the `.tfw` reader, bootloader exclusion), `native/content` plan/apply (the switch: add move-to-blobs; "modified" stops only for files of no record), `xyf_stage2` header, `xyf_entry.py` (writes the new keys and lists). Replaced: `packages.py`'s staging tree (`payload/`, `companions/`, `INCOMPLETE`) by the entry layout; `update_plan.py` stays a host review tool.
**Unproven:** rename on the device and its power-safe replace, of folders too [U 009]; hashing 126 MB per switch (else trust the record, hash only in repair); RAM for ~840 content items on A. **Rejected:** a package database (drifts from file copies); JSON manifests; per-entry full content copies; keeping every `.tfw`; version ranges or a solver; moving boot state off the slots now.
