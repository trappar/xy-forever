**Question:** what extensions are, how open-xy attaches them, and how each becomes an on/off package in 008's base-plus-modules assembly, with nothing loaded when off.

## Answer in brief
An extension is one compiled object plus a few metadata fields. It owns **no firmware edits**. Its hooks are SDK "services" in the profile, as for machines: one service (`extensions`, 7 hooks) feeds every event extension, and one (`master_filter`, 8 hooks) feeds every master processor. Each service is applied only when a selected extension needs it [C `docs/extensions.md`, `core.mjs linkKit`]. So an extension fits 008 as one package that names the services it uses. The base already holds every edit as data. Off: the object is not linked, the service stays unapplied (stock bytes) when no other extension needs it, and the accessor symbols go to `kit_absent`. **Extensions can be in the first version** (5.4): the same mechanism, about 250 device lines and 120 host lines more, checked byte for byte with `core.mjs`, which takes the extension list as an argument.

## How they attach (evidence)
- **Made of** [M]: one object per extension, `sdk/extension_<id>.o`, tagged `extension:<id>` in the kit. capture: 4,736 B file, 8,100 B in memory (5,864 B of it BSS), no imports. DJ filter: 41,396 B file, 36,208 B in memory; it imports 3 SDK master-processor symbols, the arithmetic helpers and `_memset`. Neither names a stock address, a machine or another extension. Required export: `sdk_extension_<id>_hooks`, plus `_processor`/`_panel` (or `_filter`) for a processor [C `openKit`].
- **SDK service objects** [M]: `extensions` = `extension_runtime.o`, `extension_collection.o`, `extension_stock.o` (5,220 B). `master_filter` = `master_filter_stock/hooks/panel.o` (4,936 B). In every build, extensions or not: `master_filter_state.o` + `master_filter_collection.o` (1,992 B, the companion support that reads saved processor state).
- **Selection → edits** [M, Node linkKit, fm2op alone]: none 73 edits / 148,120 B allocated. capture 80 / 161,440 (+13,320). DJ filter 88 / 194,484 (+46,364). Both 88 / 202,584 (+54,464). The 7 edits = the `extensions` hooks (controller update, key queue, live note on/off, recorder tick, stop, note accepted). The 8 = the `master_filter` hooks (MIX buttons, shifted buttons, encoder, EQ frame, parameter receiver, audio call, project publication, new project). Any extension turns on all 7, even one that takes no events. A hook's bytes depend on where `sdk_extensions_*` lands, so they depend on the selection, as 008 found for machine services.
- **Selection rules** [C `extensionSelection`, `linkKit`]: at most 16 extensions. The order is collection order, never tick order; it is the callback order. Two extensions with the same claim are refused (staging: the same for `drumline_page`). Master processors need unique `state_id` and asset names, and several may be included (the chooser lists them). `linkKit` needs at least one machine. Unselected extensions' accessors alias `kit_absent`. Extensions take no machine numbers.
- **Generation-bound** [M]: `extension_collection.o` and `master_filter_collection.o` name every kit extension. The interface is source-level, not a binary ABI [C]. So an extension package works only with the base from the same export, as machines do.
- **Not in the kit** [C `tooling/browser_kit.py`]: extension entries carry no source pin and no licence (notices cover only the SDK, the runtime and machines' `vendor/LICENSE`).

## Design
- **Package** `ext/<id>` (host packager, from the kit; no open-xy change): the object unchanged; its link-order key; `uses` (`extension`, plus `master_filter` for a processor; staging adds `drumline_page`); `exclusive` (claims; staging adds `drumline_page`); the accessor symbols to alias when off; name, description, note, origin, claim labels, actions; the processor's state id and SVG with its SHA-256; source (repository, tag, commit) from `catalog/extensions.json` at the kit's commit. **No edits, no addresses.**
- **Base** (as 008) also holds the extension order of its generation and the service objects above. Its edit list is the whole profile, unchanged.
- **Assembly**: services = 008's machine rule ∪ the `uses` of each selected extension, matched against `profile.services`. All else is 008's linker and patcher. The rule lives in host-made data, so the device needs no code for a new capability unless the capability brings new edit kinds or link rules.
- **Shared edits and order**: services are shared, never owned. One copy serves all subscribers and is applied once (union). `patchFirmware` refuses overlapping intervals across the whole profile, so no two services conflict. Edit order does not matter; object order is the kit's, and callback order is the collection's.
- **What "off" does** [C/I]: capture keeps no saved state, so Record double-tap is stock again. DJ filter: projects open with stock EQ (the stock EQ values stay in `.xy`). A save made while it is off drops the DJ choice and settings, because the SDK writes `open-xy.master-filter` only when a processor is linked [C `projects.md`; I]. Turning it back on before saving restores them. Drumline page (staging): pads play as stock; whether a save keeps their settings is [U].

## What changes in 5.4a-e (all in v1)
- **5.4a** packager: extension packages, source pins from the catalog, `uses`/`exclusive`/accessor lists; the recombination test covers every `extensionChoices(kit)` (4 for 0.0.6). ≈ +100 lines Python.
- **5.4b** linker: extension validation (ids, claims, collection order, ≤ 16), the object filter, absent-extension aliases, services from `uses`. ≈ +80 lines C++.
- **5.4c** patcher and content: no new edit kind. The processor SVG goes into the entry's content delta as `display/<asset>`, with the asset-collision check. ≈ +30 lines.
- **5.4d** job: the selection and the entry's inputs record extensions, and `layout.json` gets `extensions` (as the builder writes it; 5.2a keeps it). ≈ +20 lines.
- **5.4e** Mods page: an Extensions section, a conflict message ("both use Record double-tap"), the meter counting the object plus first-use service bytes, extension ids in `xyf_host.py mods`. ≈ +80 lines + previews.
- **Byte check**: run `linkKit(kit, sel, layout, ext)`, `patchFirmware` and `buildAssets(…, ext)` for every extension choice crossed with every subset of the 7 `linked` machines and with 008's 20 random selections. The module, `os.ldr`, layout and content must be identical. The kit's own export probably already proves `linked` + all its extensions against GNU ld [I: native builds include the whole collection, `docs/extensions.md`].

## Safety
At assembly, as 008 plus: every profile edit's preimage and mapping match stock, active or not (`patchFirmware`). Only the base's edits (profile SHA-256 pinned) are applied; a package carrying edits or addresses is refused. Our packager also refuses an extension object that imports anything but SDK or runtime exports (stricter than `core.mjs`, bytes unchanged). Every hook lands inside the module, no intervals overlap, and undoing the edits and removing the record gives stock's SHA-256. The image keeps 008's shape (one loader record at `0x8d2d0380`) and must pass the library's cold LDR policy (`target/cold.cpp`: allowed ranges, protected ranges) like any entry. **User experience:** the new entry is offered as boot once. If it hangs, a power cycle boots the old default, and PLAY at power-on opens the XY Forever menu (turn the extension off, Apply). An extension's code runs only on use (capture on a double-tap while playing; DJ filter once chosen), so boot once proves less than it does for a synth: try the feature in that session before making the entry the default.

## What 008 needs to change
"No extensions" in the first version, and stage 2 "extensions as toggles", become stage 1 (stage 2 keeps rollback). The service rule gains the extension uses. Absent aliases cover extensions too. Content gains the processor artwork. The kit has 79 machine entries [M] (008 says 80).

**Unproven:** `checkpoint` and `drumline_page` (not in the kit; staging's handling of an absent drumline processor not read); extension licences; DJ settings dropped by a save while off [I]; whether boot once catches extension faults. **Rejected:** an extension package carrying its own edit list (the sites are shared and SDK-owned, each applied once); applying the services always with a runtime enable flag (stock code changes and memory is used while off); patching an extension into an assembled image; zero-machine builds in v1 (`linkKit` refuses them, so there is no reference to compare with). **Open questions:** (1) extensions in the first version? (2) an extension needs at least one mod on: acceptable? (3) offer community extensions (DJ filter) beside Core capture?
