# 008: On-device mod selection (plan item 5.3)

Research record, 2026-11-14, against open-xy `4718876` (branch `sdk/synth-postmix`, 0.0.4) and the published kit 0.0.6 (`opxy-browser-kit/1`, SDK `52c8de9`, 80 machines, 395 objects, 205 profile edits) (the private fixture `paths.PUBLISHED_KIT`). The core-machines repository is not checked out; its compiled objects are in that kit. No device, no firmware build, no network. **[C]** read from code/docs, **[M]** measured (kit objects parsed; probes compiled with `../tools/blackfin`), **[I]** inferred, **[U]** unverified.

**Question:** can XY Forever assemble a firmware from a base plus the chosen mods, once per selection change, so unchosen mods use no memory; what does it take, and what is the smallest first version.

## Answer in brief
Practical, at moderate cost. 005 rated "link at boot" high because it assumed linking at every boot and a format of our own. Open-xy already ships what a device linker needs: its kit holds normalized ELF32 relocatable objects per machine plus SDK objects, and `builder/core.mjs` is a ~400-line reference linker (`readObject`, `numberLayout`, `linkKit`, `patchFirmware`, `buildAssets`) whose output the kit export checks against GNU ld byte for byte [C]. We port that linker to freestanding C++, run it once when the user presses Apply, and store the result as an ordinary library entry. Every output can be proven on the host: it must be byte-identical to `core.mjs` on the same inputs. **First version:** packages split from one open-xy kit, catalog machines only, OS 1.2.1 only, no extensions.

## Evidence
- **Base (Q1)** [C profile, M counts]: the 205 edits are 26 fixed byte edits (2 heap, 21 relocated-table, 3 text), 4 `aux` text edits, 36 hooks plus the startup label that branch to SDK symbols, 10 profiling-off hooks, and 128 hooks in 9 services (samples 63, drums 17, aux 9, control 8, master_filter 8, extensions 7, players 7, drum_sends 5, drum_locks 3, octaves 1). A service is applied only when a selected machine's kind needs it. Hook bytes depend on where the module's symbols land, which depends on the selection. So a prebuilt "base os.ldr" would save only the 26 fixed edits, would lose byte parity, and needs TE's OS on the host. **Base = the library's official `opxy-121-stock` os.ldr (SHA-256 pinned by the profile) + the edit list as data, applied at assembly.**
- **Selection-dependent code** [M]: the per-collection SDK objects (`startup.o`, `benchmark.o`, `synth_control_table.o`, `project_companion_table.o`, `sample_callbacks.o`, `drum_callbacks.o`, `player_table.o`, …) are compiled for the kit's whole collection. They name each machine's callbacks (~7 per synth). An unselected machine's callbacks resolve to `kit_absent` (its `absent` map), and its numbers are absolute symbols set to 0 (`numberSymbols`). These rows cost ~36 KB for 80 machines, about 0.45 KB per unselected machine. The machine's code, data and state are not linked.
- **Module (Q2)** [M]: a machine is 4 to 6 objects (fm2op: `voice.o`, `display.o`, `screen.o`, `registration.o`). Sizes: ringmod 2.4 KB; fm2op 18 KB plus 7.5 KB state; karplus 16 KB plus 82 KB; macroosc 257 KB plus 162 KB; troupe 905 KB plus 92 KB. The SDK core is 103 KB plus 20 KB state; the samples service adds 16 KB plus 130 KB. An fm2op-only module: 120,524 B initialized, 148,120 B allocated. Machines import only SDK symbols (25 to 35 per synth, 6 to 9 per effect) and their own `<prefix>_engine_id/_page_id/_fx_id`: no stock address, no other machine, no shared DSP library (vendored code is private to each machine). The SDK imports 11 stock addresses (`kit.definitions`). Arithmetic helpers (`sdk/runtime/_muldi3.o`) are linked only when referenced (`selectRuntime`).
- **Relocations** [M]: only 5 types occur, counted over the whole kit: `R_BFIN_LUIMM16` (6) 13,214, `R_BFIN_HUIMM16` (7) 13,214, `R_BFIN_PCREL24` (10) 9,540, `R_BFIN_PCREL24_JUMP_L` (13) 521, `R_BFIN_BYTE4_DATA` (18) 17,464. All are RELA; `readObject` refuses anything else, plus COMMON, weak, merge and COMDAT sections [C]. The kit's 7 `linked` machines: 105 objects, 690 globals, 9,994 relocations, 1,174,992 B. The whole kit: 2,893 globals, 53,953 relocations, 8.68 MB of objects; the largest object is `troupe/voice.o`, 896,192 B.
- **Toolchain options** [M]: `-fPIC` changes nothing on bfin-elf (still LUIMM/HUIMM). `-mid-shared-library` emits `R_BFIN_GOT` and `BYTE2_DATA` and needs P5 set on every OS-to-module call. `-mfdpic` emits `GOT17M4`. Data pointers (BYTE4) need relocation in every option. Earlier work, since removed: a kit replay script with GNU ld parity and a 60-line relocation kernel (host-checked, never run) [C].

## Design
- **Packages (host tool, from an open-xy kit, no open-xy change):** `base` per kit generation: the profile edits in binary form, SDK and runtime objects in link order, definitions, `fixed` numbers, stock-catalog hash and insertion offsets, service fallbacks. One package per machine: its objects unchanged (ELF, so `core.mjs` can relink the same bytes), its `absent` map, kind and flags, link-order keys, its catalog entry with the number position marked, its finished svg and presets, and its source (repository, tag, commit) and licence. Kit sources: the published `kit.json` (catalog machines, already compiled), or `sdk.py kit --personal` for the user's own machines, which re-exports the whole generation. The device refuses packages of different generations. Cache: `/yaffs2/xy-forever/mods/<profile>/<generation>/` (~8.7 MB for the whole catalog [M]).
- **Assembly (Q3)**, on the processor that owns NAND (A) [I], as a job split into steps in its poll loop so link keepalives continue: (1) read the selection and the device layout; (2) number the machines (`numberLayout`); (3) read each object's headers and place sections text, rodata, data, bss in kit order from `0x8d2d0380`, within 2032 KiB; (4) build the global table, then the absent aliases; (5) copy each object's bytes into the module buffer and apply its relocations, checking each like `core.mjs` (opcode, ±16 MiB range, overlap, unresolved); (6) patch stock: services, hooks redirected to symbols, profiling off (the website's mode); append one loader record before FINAL; (7) self-check: undo the edits and remove the record, then the SHA-256 must equal stock; `native/ldr` inspect; (8) content delta (Q5); (9) admit (Q8). RAM ≈ 6 MiB of SDRAM, which is free while the menu runs [I]: module ≤ 2,080,768 B, stock 2,373,336 B, one object ≤ 1 MiB, tables < 0.2 MB. It needs a memory-map entry clear of file staging (`0x8b800000..0x8c000000`) and the reporter. Time [I]: CPU < 0.1 s at 400 MHz for ≤ 54k relocations; reads ~4.4 MB at 4.9 MB/s [C] ≈ 1 s; writing ~2.5 MB plus content [U write speed]; so a few seconds to ~10 s.
- **Numbers and projects (Q4)** [C core.mjs/api.md]: one device layout per profile (`mods/<profile>/layout.json`, `opxy-layout/1`). It only grows: every number ever given out stays held, the 4 `fixed` machines keep theirs, and new machines get FNV-1a places in ID order. So a machine's numbers never depend on what else is selected. It is seeded from `/yaffs2/layout.json` (left by a web-builder install [C 006]) or from an imported entry's layout, so existing projects keep their numbers. It is written only after an entry is admitted. A project using an inactive machine opens with Prism (18), or no effect on a send, through open-xy's companion code; a save keeps Prism [C 005]. The number is never reused, so re-enabling the mod before saving restores the track. A notice in our menu is not planned.
- **Content (Q5)** [C `buildAssets`]: three things depend on the selection. `op1_factory.json` is the official file (hash-pinned) with each machine's entry inserted at 3 fixed offsets (engine 4435, fx 1583, seq 2565); an effect's entry carries its number, a player's carries the number + 4. Then `display/<id>.svg` and `presets/<id>/*.json`, prebuilt in the package. The assembled entry stores these as its content delta in `firmware/<id>/content/`, the same shape as an imported builder ZIP. 5.2e's switch applies it over the official content (4.6c) when the entry becomes the default, and removes files of mods no longer in the delta, as a package manager does. Stock's handling of catalog entries for absent machines stays 5.2d's question [U].
- **Firmware versions (Q6)** [C]: each machine's code is compiled inside 1.2.1 platform templates (`voice.cpp.in` and others include `stock.hpp` with 17 stock addresses and `screen.hpp` with 15), and only the `opxy-1.2.1` profile exists. Packages are therefore per profile; the device cannot compile. The cache keeps compiled packages per profile plus each package's source identity, so a host rebuilds them for a new profile. After the OS version changes, the device re-assembles with that profile's packages, or says a host rebuild is needed. 1.2.5 needs open-xy's port (`docs/porting.md`, maintainer work with a device) and SAFETY's 1.2.5 rules first.

## Safety (Q8)
Assembly writes only a new library entry (`firmware/<id>/`: temp file, read-back SHA-256, `info.txt` last as in 003) and, on default change, `content/` through 5.2e. It never touches the boot partition, the bootloader, SPI, `bootloader.dev` or `user/`. Before admission, the device runs all of `core.mjs`'s link and patch checks plus the stock-reconstruction check. It records its inputs (generation, selection, layout, package hashes) in the entry so `xyf_host.py` can relink and compare bytes. A new entry is offered as **boot once**; the default changes only after the user says it worked. If it hangs or crashes, a power cycle returns to the old default, and holding PLAY at power-on opens XY Forever's menu, which is still available because it runs from the boot partition before any entry [C ARCHITECTURE]. The dev menu (COM) remains below that. All of this is recoverable without hardware [I]. A faulty mod still runs unsandboxed inside the OS, as any open-xy build does today [C README].

## Sizing, risks, proofs (Q9)
- **Device** (freestanding C++, fixed arrays, no heap) [I]: ELF subset reader ~200 lines; linker with runtime closure, placement, symbols, aliases and relocations ~350; numbering plus layout writer ~300; patcher plus self-check ~200; content delta ~150; job and admission ~200; Mods menu page ~250. **≈ 1,650 lines**, plus ~600 lines of host tests. **Host** (Python) [I]: kit splitter ~350, push/apply/verify commands ~250, layout seeding ~50: **≈ 650 lines**.
- **Risks:** (1) generation coupling: machine objects only work with the SDK objects from the same export, so a non-catalog mod or a new SDK release means a host re-export of every package. (2) Format churn (166 → 205 edits in weeks [C]): the profile is data, but new edit kinds, relocation types or object rules need a device update; refuse unknown versions. (3) The ~6 MiB scratch region and keeping the job step-bounded on A. (4) Content consistency (5.2d). (5) Unverified write speed.
- **Provable on the host:** byte-identical module, layout, `os.ldr` and content against `core.mjs` (itself checked against GNU ld) for many selections, using the same C++ compiled for the host; numbering against `open-xy/tests/fixtures/numbers.json`; every rejection; a power cut at every write. **Device only:** memory fit, time, the file engine's writes, and that an entry assembled on the device and pulled back is byte-identical (the decisive test). Booting is then the same as booting a web-builder build.

## Reuse and licences (Q7)
The SDK, builder, linker script and profile are MIT [C `LICENSE`]. Porting `core.mjs` and the profile into XY Forever is allowed with the notice kept. Kit notices [M] carry MIT (SDK and several machines), the GCC arithmetic runtime (GPL-3.0+ with the runtime exception) and one AGPL-3.0 text; Timestretch is AGPL, and builds that include it are AGPL [C README]. Most machines' licences are not in the kit [U]. The catalog requires redistributable licences [C `docs/catalog.md`]. For personal use nothing forbids this. If we ever publish packages, ship each one's notices and source pointer (repository and commit). Nothing found forbids the approach.

## Rejected
Linking at every boot (boot-time risk and cost). An enable table in one big build (user: memory). PIC (measured: no PIC on bfin-elf without GOT, P5 setup and data relocations anyway). Modules pre-linked into fixed slots (wastes the shared 2032 KiB; numbers and SDK tables still depend on the selection). A prebuilt base `os.ldr` (above). Copying the 21.6 MB `kit.json` to the device (it holds wasm previews and base64).

## Stages
1 (= 5.4) one kit generation, catalog mods, 1.2.1, no extensions: choose on the device; unchosen mods use no memory beyond ~0.45 KB of SDK table rows each. 2: extensions as toggles; keep the previous assembled entry for rollback. 3: our own table-driven SDK tables (rows in each mod's package, gathered by the linker), so packages stop depending on the collection, the 0.45 KB rows go, and adding a mod needs no re-export. 4: other OS versions, once a profile exists.

| Item | Done when |
|---|---|
| 5.4a build: mod packages (host) | kit → `base` + one package per machine (contents above); recombining them gives a kit whose `core.mjs` links match the original's byte for byte for the `linked` selection and 10 others; tests |
| 5.4b build: native linker | `native/mod_link.*`: module, globals and layout byte-identical to `core.mjs` for every subset of the 7 `linked` machines and 20 random catalog selections; numbers equal `numbers.json`; every `core.mjs` rejection reproduced |
| 5.4c build: native image + content | patched `os.ldr` (profiling off) and `op1_factory.json`, svg and presets byte-identical to `patchFirmware`/`buildAssets` (private stock fixture); self-check rejects tampering |
| 5.4d build: assembly job | cache layout, scratch memory-map entry, step-bounded job on A, temp/read-back/`info.txt` admission, device layout persistence, serial `MODS_APPLY`/`MODS_STATUS`; simulator: a power cut at every write leaves library and layout valid |
| 5.4e build: Mods page | list with toggles and a memory meter (2032 KiB), Apply → progress → boot-once offer; `ui_preview.py` screens; `xyf_host.py mods push/apply/verify` |
| 5.4f device safe: dry run | fm2op + ringmod assembled on the device, pulled back, byte-identical to `core.mjs`; time and RAM recorded; nothing booted |
| 5.4g device risky: first boot | that entry booted once with its content (5.2e); user: booted, mods listed; a power cycle returns to the default |
| 5.4h device safe: toggle round trip | add karplus, drop fm2op, assemble; fm2op's numbers still held; its content removed; the old default untouched |

Needs: 5.4a after 5.2a; 5.4d after M2's file engine, 5.4b and 5.4c; 5.4g after 5.2e.

**Unproven:** write speed and job time on the device; the scratch region; stock behaviour with catalog entries for absent machines (5.2d); licences of most community machines. **Open questions:** (1) may version 1 take its mod packages from open-xy's own kit (published catalog; own mods by re-exporting the whole set on the computer)? (2) community catalog mods in the list, or Open-XY's own first? (3) the website's mode (per-voice profiling off)? (4) extensions (capture, DJ filter) now or in stage 2?
